# 프로젝트: ODYSSEY — 귀환의 항해

당신은 시네마틱 웹 경험을 설계하는 아트디렉터이자, SVG 기반 그래픽스 엔지니어이며, 인터랙티브 스토리텔링을 구현하는 프런트엔드 개발자다.

오디세우스의 세계와 귀환 여정을 정교한 3D SVG로 표현하는 인터랙티브 웹앱을 구현하라.

결과물은 영화 소개 페이지나 줄거리 카드 모음이 아니다.
사용자가 살아 움직이는 입체 세계를 탐색하면서, 장소와 사건, 인물의 선택과 그 결과를 이해하는 “시네마틱 신화 아틀라스”다.

기획 설명이나 정적인 목업으로 끝내지 말고, 실제로 실행하고 조작할 수 있는 웹앱을 완성하라.


## 1. 핵심 경험과 콘텐츠 기준

### 핵심 경험

“고대의 항해 지도가 눈앞에서 입체 세계로 살아나고,
작은 배를 따라 이동하면서 신화 속 사건을 직접 발견하는 경험.”

사용자는 전체 세계를 조망하고, 특정 장소로 접근하고, 사건의 핵심 순간을 재생하고, 다시 항해를 이어갈 수 있어야 한다.

시각적 우선순위:
입체 세계의 완성도 → 장면 간 이동 → 이야기 전달 → 보조 정보.

기능을 많이 넣는 것보다, 바다·배·섬·괴물·궁전이 하나의 세계로 느껴지는 것이 중요하다.

### 콘텐츠 기준

영화 〈오디세이〉를 출발점으로 삼되, 아래 항해 구성은 호메로스의 《오디세이아》를 기반으로 한 확장형 콘텐츠로 취급한다.

영화에서 확인된 내용, 원작에 근거한 내용, 웹앱을 위한 시각적 해석을 구분한다.
확인하지 못한 영화의 장면·대사·등장인물 설정을 임의로 확정하지 않는다.

영화 포스터나 스틸 이미지를 화면 배경으로 사용하는 방식으로 해결하지 않는다.
배우의 얼굴을 재현할 필요도 없다.
세계와 인물은 직접 제작한 SVG 지형, 조형물, 실루엣, 상징물로 표현한다.

대사와 설명은 새로 작성한다.
지도에는 “원작 기반의 상징적 항로이며, 실제 지리적 위치를 확정한 지도가 아님”을 작게 표시한다.

전체 UI와 설명은 한국어로 작성한다.
영문은 작품명과 일부 지명 병기에만 사용한다.


## 2. 아트디렉션

### 전체 스타일

“청동기 시대 항해 유물 + 정밀한 박물관 디오라마 + 장엄한 해양 서사.”

오래된 청동 항해판 위에 바다와 섬, 건축물이 실제로 솟아오른 듯한 인상.
공간은 무겁고 장엄하되, 사용자가 탐색하기 어렵게 지나치게 어둡게 만들지 않는다.

귀여운 게임 지도, 장난감 같은 로우폴리, 네온 판타지, 일반적인 SaaS 대시보드 스타일은 피한다.

면을 나눈 입체 조형을 기본으로 하되, 중요한 물체에는 곡선과 세부 구조를 추가한다.
삼각형 몇 개로 이루어진 추상적인 섬이나 아이콘 수준의 배로 끝내지 않는다.

### 색상

- 심해 배경: #06141F
- 바다 기본색: #0B3442
- 청동과 항로 강조: #B6925A
- 석재와 절벽: #A69479
- 양피지와 주요 텍스트: #E7DDC6
- 전쟁과 위험: #A44B3F
- 신성함과 마법: #78ADA1

색상은 디자인 토큰으로 관리한다.
장면에 따라 색온도와 명암을 변화시키되, 전체 디자인 언어는 유지한다.

트로이는 잿빛과 불꽃, 키르케의 섬은 청록빛과 깊은 식생,
저승은 탈색된 회색, 이타카는 따뜻한 아침빛으로 차별화한다.

### 빛과 재질

광원의 방향을 통일하고, 물체의 윗면·옆면·그늘진 면을 구분한다.
절벽 아래에는 접촉 그림자, 수면 가까이에는 제한적인 반사광을 둔다.

석재에는 균열과 층리, 선박에는 판재와 밧줄, 돛에는 봉제선과 접힌 면을 표현한다.
재질 표현은 확대했을 때 발견되는 디테일로 사용하고, 화면 전체를 노이즈로 덮지 않는다.

타이포그래피는 제목에 절제된 명조 계열, 설명에 읽기 쉬운 고딕 계열을 사용한다.
작은 금색 글씨를 남발하지 않는다.


## 3. 화면 구성과 첫 진입

### 첫 화면

별도의 거대한 소개 화면으로 세계를 가리지 않는다.
접속 즉시 바다, 여러 섬의 입체 실루엣, 항로, 오디세우스의 배가 보여야 한다.

중앙에는 사선으로 내려다보는 입체 항해 지도를 배치한다.
왼쪽 상단에는 작은 작품명과 현재 장.
오른쪽에는 현재 사건을 설명하는 얇은 정보 패널.
하단에는 전체 여정 타임라인.
지도 모서리에는 확대·축소·시점 초기화 버튼을 둔다.

주요 진입 버튼은 “항해 시작”과 “자유 탐색” 두 개만 둔다.

기본 상태에서도 다음 움직임이 절제된 속도로 보여야 한다:
잔잔한 파도, 선박의 작은 흔들림, 멀리 흐르는 안개, 현재 위치의 부드러운 강조.

긴 로딩 연출이나 건너뛸 수 없는 인트로를 넣지 않는다.

### 데스크톱

입체 세계가 화면의 약 70~80%를 차지하도록 한다.
정보 패널은 약 300~340px 폭으로 구성하되, 지도 위 핵심 피사체를 가리지 않는다.
부가 설명은 접어서 시각적 집중을 유지한다.

### 모바일

지도를 상단의 주요 경험으로 유지하고, 설명은 접고 펼칠 수 있는 하단 시트로 제공한다.
데스크톱 화면을 단순 축소하지 않는다.
터치 조작과 설명 스크롤이 충돌하지 않도록 설계한다.


## 4. 스토리 구조

앱의 기본 진행 순서는 “귀환 여정의 시간순 재구성”이다.
영화의 편집 순서나 원작의 서술 순서와 동일하다고 표시하지 않는다.

각 장은 다음 구조로 작성한다.

장소 → 직전 사건과의 연결 → 이번 사건 → 선택 또는 갈등 → 결과 → 다음 항해.

사건을 단순히 “괴물을 만났다”로 요약하지 않는다.
이전 사건이 왜 다음 시련으로 이어지는지 드러내라.

### 항해 구성

| 장 | 장소·사건 | 서사 핵심 | 시각적 중심 |
|---|---|---|---|
| 01 | 트로이 | 전쟁 종료와 귀환 출발 | 불타는 성벽, 목마, 출항하는 함대 |
| 02 | 이스마로스 | 키코네스인들과의 충돌 | 해안 도시, 무너진 방어선, 급한 출항 |
| 03 | 로토파고이의 땅 | 귀환 의지를 잊게 하는 유혹 | 연꽃 군락, 몽환적인 해변, 느려지는 움직임 |
| 04 | 폴리페모스의 동굴 | 기지에 의한 탈출과 오만의 대가 | 거대한 동굴, 외눈박이 거인, 양 떼 |
| 05 | 아이올로스의 섬 | 바람 자루와 무너진 귀환의 기회 | 청동 성벽, 봉인된 자루, 폭발하는 바람 |
| 06 | 라이스트뤼고네스의 항구 | 함대의 파괴 | 좁은 만, 높은 절벽, 거인의 돌과 부서진 배 |
| 07 | 키르케의 아이아이에 | 변신과 체류, 다음 여정의 준비 | 숲속 궁전, 약초, 마법의 잔 |
| 08 | 저승의 경계 | 죽은 자들과 예언 | 검은 물, 흐릿한 영혼, 빛이 닿지 않는 해안 |
| 09 | 세이렌의 바다 | 유혹을 듣되 따르지 않기 | 암초, 돛대에 묶인 인물, 유혹의 파동 |
| 10 | 스킬라와 카리브디스 | 피할 수 없는 손실 | 절벽의 괴물과 깊은 소용돌이 |
| 11 | 태양신의 섬 | 금기 위반과 파국 | 신성한 소 떼, 불길한 하늘, 난파 |
| 12 | 칼립소의 오기기아 | 머무름과 귀향 사이의 갈등 | 고립된 낙원, 동굴, 수평선을 향한 뗏목 |
| 13 | 파이아케스인의 스케리아 | 환대와 귀환 지원 | 밝은 항구, 궁정, 귀환선 |
| 14 | 이타카 귀환 | 정체를 감춘 귀향 | 안개 낀 해안, 오솔길, 먼 궁전 |
| 15 | 활의 시험과 재회 | 정체 회복과 가족의 재결합 | 궁전 내부, 활, 직조물, 올리브나무 상징 |

아이올로스의 섬 재방문, 저승 방문 후 키르케의 섬으로 돌아오는 과정 등은
새로운 대형 장을 늘리지 말고 항로의 되돌림과 중간 사건으로 표현한다.

모든 장소를 같은 섬 모양에 이름만 바꿔 배치하지 않는다.
지형의 실루엣과 건축물, 날씨, 색감만으로 서로 구분되게 만든다.

### 병행 서사

오디세우스의 항해 외에 다음 두 흐름을 보조적으로 제공한다.

“이타카의 기다림”
페넬로페, 직조, 궁전의 긴장, 구혼자들의 압박.

“아버지를 찾는 길”
텔레마코스의 탐색과 성장.

별도의 대시보드를 만들지 말고, 이타카 또는 인물 선택 시 작은 보조 장면으로 보여준다.
각 항해 사건과 병행 서사가 정확히 같은 시각에 발생했다고 임의로 연결하지 않는다.

포세이돈과 아테나의 개입은 관련 사건에서만 드러낸다.
신들을 단순 인물 카드로 나열하지 말고, 바다의 변화와 길을 비추는 빛 같은 시각적 언어로 연결한다.


## 5. 핵심 3D SVG 장면의 세부 요구

모든 장에 고유한 지형, 사건 상징물, 움직임, 탐색 지점을 구현한다.
그중 아래 장면은 대표 장면으로 삼아 디테일을 집중한다.

### A. 항해하는 선박

배는 지도 위의 아이콘이 아니라, 가까이 볼 수 있는 입체 모형이다.

선체의 윗면과 양쪽 측면, 선수와 선미, 판재, 갑판, 돛대, 돛의 앞뒤 면,
밧줄, 노, 작은 인물 실루엣을 구분한다.

돛은 삼각형 하나가 아니라 바람을 받은 곡면처럼 보이도록 여러 면과 곡선으로 구성한다.
배의 방향은 실제 항로의 진행 방향과 일치해야 한다.
배 아래에는 항적과 제한적인 반사를 표현한다.

여정이 진행되면 서사에 맞게 함대, 단독 선박, 뗏목 등의 상태가 달라진다.
근거 없는 생존자 수나 자원 수치를 게임 UI처럼 표시하지 않는다.

### B. 폴리페모스의 동굴

동굴 입구와 내부를 분리하고, 전경 바위가 내부 일부를 가리도록 한다.
거인은 선박과 사람에 비해 압도적인 크기로 표현한다.

눈의 움직임, 입구의 바위, 작은 양 떼, 탈출 동선을 탐색할 수 있게 한다.
사용자가 가까이 접근하면 동굴의 어둠 속에서 내부 구조가 드러난다.

핵심은 잔혹함이 아니라 공간의 압박감, 크기의 대비, 탈출의 긴장이다.

### C. 키르케의 섬

궁전, 숲, 계단, 약초 정원, 동물 실루엣을 입체적으로 구성한다.
잔이나 약초를 선택하면 인간과 동물 실루엣 사이의 변화가 짧게 재생된다.

마법은 네온 입자 폭발이 아니라,
색의 변화, 그림자의 변형, 얇은 안개와 빛의 맥동으로 표현한다.

### D. 스킬라와 카리브디스

한쪽은 높은 절벽과 괴물, 다른 쪽은 수면 아래로 꺼지는 소용돌이.
배가 통과해야 하는 좁은 공간이 즉시 읽혀야 한다.

소용돌이는 회전하는 원 하나로 표현하지 않는다.
높이와 반경이 다른 곡선, 명암이 다른 내부 면, 중심으로 향하는 물결,
선박과의 크기 대비로 깊이를 만든다.

장면 진행 슬라이더를 움직이면 배의 위치와 괴물의 위협, 소용돌이의 상태가 함께 변한다.
조작은 사건을 살펴보는 수단이며 원작의 결과를 임의로 바꾸는 게임은 아니다.

### E. 이타카와 궁전

해안에서 언덕 위 궁전까지 이어지는 공간을 만든다.
궁전 내부는 지붕 일부가 열린 컷어웨이 디오라마로 표현한다.

기둥, 바닥 무늬, 직조기, 활, 문과 복도의 깊이를 구분한다.
활의 시험은 활시위의 장력과 화살의 경로가 읽히도록 연출한다.

마지막 장면은 과도한 축하 효과 대신,
따뜻해지는 빛, 잔잔해진 바다, 완성된 항로로 마무리한다.


## 6. 탐색과 스토리 인터랙션

### 스토리 모드

사용자가 “다음 장”을 누르면 아래 흐름이 연결된다.

현재 장면 정리
→ 항로 표시
→ 배 이동
→ 목적지로 카메라 접근
→ 해당 장소의 핵심 움직임
→ 설명 표시.

전환은 대체로 1~2초 안에서 처리하고, 건너뛰기를 제공한다.
사용자가 원할 때만 자동 재생을 시작한다.
페이지 스크롤을 강제로 가로채 장면을 진행하지 않는다.

### 자유 탐색 모드

지도를 드래그해 이동하고, 확대·축소하며, 제한된 범위에서 시점을 회전할 수 있다.
장소를 선택하면 해당 장면으로 접근한다.
“전체 지도”를 누르면 탐색 이전의 맥락을 유지하며 돌아간다.

장소마다 2~3개의 의미 있는 탐색 지점을 둔다.
탐색 지점은 단순 장식이 아니라 사건이나 세계관을 설명해야 한다.

예:
바람 자루 선택 → 봉인과 폭풍의 관계.
직조기 선택 → 기다림과 지연의 전략.
활 선택 → 정체를 드러내는 시험.

### 상태 동기화

지도 위치, 선박 위치, 선택된 장, 설명 패널, 타임라인은 하나의 진행 상태를 공유한다.

이전 장 이동과 장 건너뛰기에서도 모든 상태가 일치해야 한다.
사용자가 장을 연속 선택하면 기존 전환을 취소하고 마지막 선택을 기준으로 이동한다.

자유 탐색 중에는 자동 카메라 추적을 중지한다.
“항해 따라가기”로 추적을 복구한다.

현재 장과 사용자 설정은 로컬에 저장하고 “처음부터” 기능을 제공한다.
저장이 불가능한 환경에서도 앱은 정상 작동해야 한다.


## 7. 3D SVG 구현 방식

### 렌더링 원칙

핵심 세계는 실제 SVG 요소로 렌더링한다.
지형과 배, 건축물을 PNG·JPG·영상으로 만들어 SVG 안에 넣는 방식은 사용하지 않는다.

기본 렌더러에 Canvas, WebGL, Three.js를 사용하지 않는다.
화면 전체에 CSS rotateX를 적용하는 것만으로 3D 구현을 대체하지 않는다.

모델은 x, y, z를 가진 정점과 면으로 정의한다.
카메라 변환 후 2차원 좌표로 투영하여 SVG path 또는 polygon으로 그린다.

기본 카메라는 정사영 기반의 사선 시점으로 구성한다.
등각에 가까운 기본 각도를 사용하고, 회전 범위는 장면의 가림 처리가 안정적인 범위로 제한한다.
자유로운 360도 회전보다 잘 설계된 구도와 안정적인 가독성을 우선한다.

### 지형과 조형

섬은 해안선, 높이별 지형, 절벽 측면, 정상부로 구성한다.
불규칙한 외곽선과 일부 단차를 이용해 자연스러운 실루엣을 만든다.

건축물과 배는 앞면·측면·윗면이 실제로 구분되는 입체 면으로 구성한다.
물체의 면 방향과 광원 방향을 이용해 밝기를 계산한다.

벡터 그라디언트, 마스크, 클리핑은 재질과 분위기를 보조하는 용도로 사용한다.
필터만으로 입체감을 만들어내려고 하지 않는다.

### 깊이와 가림

카메라 기준 깊이 정렬과 필요한 면 제거를 구현한다.
겹침이 복잡한 장면은 면 분할 또는 명시적인 레이어 설계로 보완한다.

바위 뒤로 지나가는 배, 동굴 입구 뒤의 거인, 궁전 기둥 사이의 인물이
공간 관계에 맞게 가려져야 한다.

바다 아래에 있어야 할 선이 지형 위로 비치거나,
항로가 산과 궁전 위를 가로지르지 않도록 처리한다.

### 좌표 일관성

선박, 항로, 장소, 탐색 지점은 같은 월드 좌표계를 사용한다.
항로는 월드 좌표의 곡선으로 정의하고, 선박의 방향은 곡선의 접선으로 계산한다.

라벨과 HTML 정보창은 해당 월드 좌표를 화면 좌표로 투영해 배치한다.
줌과 회전 이후에도 클릭 영역과 화면상의 물체가 어긋나지 않아야 한다.

글자는 지형처럼 기울이지 않고 화면에 읽기 좋은 방향으로 유지한다.
라벨이 겹치면 우선순위에 따라 일부를 숨긴다.


## 8. 애니메이션과 성능

움직임은 공간의 생동감과 사건 전달을 위한 것이어야 한다.
모든 요소를 동시에 움직이지 않는다.

정지 상태:
파도, 돛, 안개 등 소수의 느린 움직임.

항해 상태:
배 이동, 항적, 카메라 이동.

사건 상태:
선택된 장면의 핵심 애니메이션.

활성 장면에만 높은 디테일을 사용한다.
전체 지도에서는 단순화된 모델, 확대 시에는 정교한 모델을 사용하되
전환 과정에서 다른 물체로 바뀐 듯한 시각적 단절이 없어야 한다.

정적인 지형의 계산 결과를 캐싱하고,
카메라 또는 모델이 바뀐 경우에만 필요한 좌표를 갱신한다.

매 프레임 React 상태를 변경해 전체 앱을 다시 렌더링하지 않는다.
장면 렌더러와 UI 상태의 책임을 분리한다.

애니메이션 시간은 하나의 공통 컨트롤러에서 관리한다.
탭이 비활성화되면 애니메이션을 멈추고,
일시정지와 모션 축소가 모든 장면에 일관되게 적용되도록 한다.

화면 전체에 움직이는 turbulence, blur, displacement 필터를 겹쳐 사용하지 않는다.
그림자와 안개는 국소 영역에 제한한다.

데스크톱은 부드러운 60fps를 목표로 하되 성능을 측정하지 않고 달성했다고 주장하지 않는다.
저성능 환경에서는 입자 수, 파도 수, 그림자, 모델 세부도를 단계적으로 줄인다.
핵심 스토리와 조작 기능은 유지한다.


## 9. 접근성과 조작

키보드로 장 선택, 이전·다음 이동, 재생·정지, 패널 닫기가 가능해야 한다.
지도와 동일한 장소를 선택할 수 있는 텍스트 목록을 제공한다.

버튼과 탐색 지점에는 명확한 이름과 포커스 표시를 부여한다.
hover에서만 정보를 제공하지 말고 클릭과 터치로도 접근할 수 있게 한다.

운영체제의 prefers-reduced-motion 설정을 존중한다.
모션 축소 시 카메라 비행과 반복 움직임을 제거하고,
즉시 전환 또는 짧은 페이드로 대체한다.

일시정지 상태에서도 텍스트와 장면을 충분히 살펴볼 수 있어야 한다.
빠른 번쩍임과 강한 화면 흔들림을 사용하지 않는다.

음향은 필수 범위에서 제외한다.
실제 기능이 없는 음향 버튼을 장식으로 배치하지 않는다.


## 10. 개발 구조

기존 프로젝트가 있으면 해당 환경과 규칙을 먼저 확인하고 유지한다.
신규 프로젝트라면 React + TypeScript + Vite를 기본으로 한다.

백엔드, 로그인, API 키 없이 정적 배포 가능한 구조로 구현한다.
런타임에 영화 API나 외부 이미지 검색 서비스에 의존하지 않는다.

다음 책임을 분리한다.

- 콘텐츠: 장소, 인물, 사건, 출처, 항로.
- 그래픽 엔진: 좌표, 카메라, 투영, 깊이 정렬, 조명.
- 모델: 배, 지형, 건축물, 괴물, 소품.
- 장면: 장소별 구성과 사건 애니메이션.
- UI: 타임라인, 설명 패널, 탐색 메뉴, 설정.

권장 데이터 항목:

Chapter:
id, order, title, locationId, summary,
cause, conflict, consequence, nextChapterId,
characterIds, sourceType, sourceRef, sceneId.

Location:
id, name, worldPosition, terrainType,
palette, landmarks, hotspots.

Scene:
id, cameraPreset, modelIds, lighting,
ambientMotion, eventAnimation, qualityLevels.

sourceType:
film-confirmed / original-epic / creative-interpretation.

한 컴포넌트에 모든 SVG와 스토리를 몰아넣지 않는다.
원작 기반 텍스트와 시각적 연출 설정을 분리해 수정 가능하게 한다.

재사용 모델은 공유하되, 각 장소의 구성과 실루엣은 독립적으로 설계한다.
한 개의 섬 컴포넌트에 이름과 색만 바꾸는 방식은 허용하지 않는다.


## 11. 구현 순서와 완료 기준

먼저 전체 지도, 선박, 카메라 투영, 트로이에서 첫 목적지까지의 이동을
실제로 작동하는 하나의 흐름으로 완성한다.

다음으로 대표 장면의 조형과 사건 연출을 정교하게 만든다.
이후 나머지 장을 동일한 인터랙션 구조에 연결한다.

기능 수를 늘리기 위해 대표 장면의 품질을 낮추지 않는다.
동시에 일부 장을 “준비 중”으로 남겨 전체 서사를 끊지 않는다.

아래 기준으로 결과를 검증한다.

1. 첫 화면에서 바다·입체 지형·선박·항로가 즉시 읽힌다.
2. 확대하면 선박과 건축물에 추가적인 디테일이 보인다.
3. 회전하면 면의 방향과 가림 관계가 실제로 달라진다.
4. 15개 장을 처음부터 끝까지 이동할 수 있다.
5. 장면마다 고유한 지형과 의미 있는 상호작용이 있다.
6. 타임라인, 선박, 카메라, 설명 패널이 동기화된다.
7. 이전 장 이동과 연속 클릭에도 상태가 깨지지 않는다.
8. 모바일에서 지도 조작과 설명 읽기가 모두 가능하다.
9. 모션 축소와 일시정지가 전체 장면에 적용된다.
10. 빌드와 타입 검사를 통과하고, 빈 버튼과 잘못된 링크가 없다.

브라우저 확인 도구가 제공되면 데스크톱과 모바일 크기에서 직접 조작하고,
스크린샷으로 겹침, 잘림, 가독성, 입체감을 검토한 뒤 수정한다.

실제로 실행하지 못한 검증 항목은 완료했다고 쓰지 않는다.

최종 결과에는 실행 가능한 프로젝트와 실행 방법,
구현된 주요 기능, 실제 검증 결과, 남아 있는 제약을 제공한다.

가장 중요한 판단 기준:

“영화 줄거리를 읽는 웹페이지”가 아니라,
“오디세우스의 세계 안에서 항해하며 이야기를 이해하는 정교한 입체 경험”인가?
